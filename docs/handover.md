# 인수인계 체크리스트

담당자가 바뀔 때(퇴사·부서 이동) **무엇을 넘기고, 새 담당자가 무엇부터 확인해야 하는지**를 순서대로 적은 페이지입니다.
이 문서만 따라가면 "접속 → 권한 확보 → 상태 확인 → 변경 작업"까지 혼자 할 수 있게 쓰는 것이 목표입니다.

!!! note "사내 전용 정보는 여기 없습니다"
    접속 주소, 서버 PC 로그인 계정, 관리자 계정, GitHub 계정, 러너 토큰 같은 값은 이 공개 문서에 넣지 않습니다.
    **사내 인수인계 문서와 USB 패키지 안의 문서**에 있으니, 인계 자리에서 그 위치를 먼저 확인하세요.

## 1. 첫 90분 — 이 순서로

| 순서 | 할 일 | 됐다고 볼 수 있는 신호 | 시간 |
|---|---|---|---|
| 1 | 사내망 PC에서 허브 주소를 열어 본다 | 로그인 화면이 뜨고 하단에 관리자 이름이 보임 | 5분 |
| 2 | 내 계정으로 가입 → 기존 관리자에게 **승인 + 관리자 권한** 요청 | 오른쪽 위가 `내 이름 · 관리자`, **계정 관리** 탭이 보임 | 15분 |
| 3 | 코드 저장소 접근 확인(비공개) | 저장소가 열리고 **Actions** 탭이 보임(404 면 권한이 없는 것) | 10분 |
| 4 | 러너 상태: 저장소 → Settings → Actions → Runners | 서버 PC 러너가 **Idle(초록)** | 5분 |
| 5 | **서버 진단** 워크플로우 한 번 실행(Actions → Run workflow) | 초록 체크. 로그에 예약 작업 4개가 모두 있고 `Logon=S4U`, 포트 8002 리스닝 | 15분 |
| 6 | **데이터 점검** 워크플로우도 한 번(읽기 전용) | 계정·승인 대기·필수 항목 미기입 현황이 표로 출력 | 10분 |
| 7 | 진단 로그에서 `deploy.log`·`server.log` 꼬리 구획 찾아 두기 | 다음에 장애가 났을 때 어디를 볼지 알게 됨 | 10분 |
| 8 | 개발 PC에 저장소 클론 → 로컬에서 화면 띄워 보기 | `http://127.0.0.1:8002` 에서 화면이 열림 | 20분 |

!!! tip "5번을 꼭 해 보세요"
    서버 PC는 원격 접속(RDP·WinRM·공유)이 막혀 있어서, **진단 워크플로우가 원격에서 서버를 들여다보는 유일한 수단**입니다.
    장애가 났을 때 처음 써 보면 늦습니다. 평상시에 한 번 돌려 정상 상태의 로그 모양을 봐 두세요. 자세한 읽는 법은 [서버 PC 운영](operations.md) 4절.

## 2. 권한·자격 이전 목록

| 대상 | 무엇을 | 이전 방법 |
|---|---|---|
| 허브 관리자 계정 | 가입 승인, 권한 변경, 비밀번호 초기화, 과제 승인 | 기존 관리자가 **계정 관리 → 관리자 명단**에 새 담당자를 추가(아직 가입 전이면 이메일만 올려 두면 승인 시 자동으로 관리자가 됩니다). 관리자는 여러 명, 우선순위 없음. **본인 해제는 불가**이므로 새 담당자가 관리자가 된 뒤 떠나는 담당자를 내립니다 |
| 코드 저장소 | 비공개 저장소 `SinokorOfficial/finance-team-hub` 읽기·쓰기 | GitHub 조직의 해당 팀에 새 담당자 추가(조직 관리자 작업). 저장소 설정을 만지려면 admin 권한도 필요 |
| 문서 저장소 | 이 공개 문서 사이트(GitHub Pages) | 같은 조직에서 쓰기 권한 부여. `docs/`·`mkdocs.yml` 이 main 에 push 되면 자동으로 다시 빌드됩니다 |
| self-hosted runner | 자동 배포용 러너 등록·재등록 | 저장소 Settings → Actions → Runners 접근 권한. 재등록 토큰은 그 화면에서 발급(유효 1시간)하며 **문서에 적어 두지 않습니다** |
| 서버 PC 로그인 계정 | 예약 작업 등록, 배치 실행, 로그 직접 확인 | 전산팀·기존 담당자와 함께 서버 PC 앞에서 인계 |
| 사내 문서·USB 패키지 | 접속 주소, 설치 절차, 실측 설치 기록 | 실물 USB와 사내 문서 위치를 인계 자리에서 확인 |

!!! warning "서버 PC 로그인 계정이 바뀌면"
    예약 작업 4개는 등록 당시 로그인 계정의 SID로 박혀 있습니다. 계정을 바꾸면 작업이 실행되지 않으므로,
    새 계정으로 로그인한 뒤 `server\tools\작업등록.bat`(감시·첨부 백업)과 `tools\예약작업_재등록.bat`(서버·DB 백업)을 다시 실행하고, 2분 뒤 작업이 남아 있는지 확인해야 합니다.

## 3. 반복 운영 업무

| 주기 | 업무 | 어디서 |
|---|---|---|
| 매일 | 가입 **승인 대기** 확인·처리(탭 이름 옆 숫자 배지) | 화면 → 계정 관리 |
| 매일 | 과제 **승인 대기** 처리(등록·수정·삭제 요청). 변경 비교표를 보고 승인 또는 반려(사유) | 화면 → 프로젝트 |
| 주 1회 | **데이터 점검** 워크플로우 실행 → 필수 항목(사용안내·효과 지표) 미기입 과제와 **담당자 계정 미연결** 과제 확인, 해당 담당자에게 보완 요청 | Actions → 데이터 점검 |
| 주 1회 | 백업 확인: `backup\hub-YYYYMMDD.db` 가 어제 날짜까지 생성되어 있는지, `backup_uploads.log` 마지막 줄이 정상인지 | Actions → 서버 진단 |
| 주 1회 | **서버 진단** 워크플로우로 예약 작업 4종 상태·`watchdog.log` 확인(감시 로그에 기록이 늘고 있으면 서버가 반복해서 죽는다는 뜻) | Actions → 서버 진단 |
| 월 1회(또는 기획팀 요청 시) | **그룹 양식** 내보내기 → 그룹 AX 대시보드 제출. 내보내기 전에 필수 항목 미기입분을 먼저 채웁니다(비면 대시보드에서 '보완필요'로 표시됨) | 화면 → 프로젝트 → `[그룹 양식]` |
| 수시 | 비밀번호 초기화·계정 비활성화·권한 변경 요청 처리 | 화면 → 계정 관리 |
| 수시 | 팀원 신규 가입이 끝난 뒤 **담당자 계정 연결 실행** 1회 | 화면 → 계정 관리 |

## 4. 변경 작업 표준 절차

```mermaid
flowchart LR
  A["hub.html 수정<br/>(화면은 이 파일 하나)"] --> B["python server/build_static.py"]
  B --> C["로컬 확인<br/>127.0.0.1:8002"]
  C --> D["git commit → push (main)"]
  D --> E["GitHub 검사<br/>문법 · 빌드 최신 여부"]
  E --> F["서버 PC 러너가<br/>deploy.ps1 실행"]
  F --> G["Actions 초록 체크<br/>= 반영 완료 (2~3분)"]
  G --> H["문서 갱신<br/>docs/ · 변경 이력"]
```

1. **`hub.html` 만 고칩니다.** `server/static/index.html` 은 빌드 산출물이라 직접 고치지 않습니다.
2. `python server/build_static.py` 로 `static/index.html` 을 다시 만듭니다. **빠뜨리면 CI 검사에서 막힙니다**(GitHub 쪽 검사가 다시 빌드해 커밋된 파일과 비교합니다).
3. 로컬에서 서버를 띄워 확인합니다. 테스트용 DB를 쓰려면 환경변수 `HUB_DB` 에 경로를 지정합니다.
4. `git add -A` → `git commit -m "무엇을 고쳤는지"` → `git push`(main).
5. 저장소 **Actions** 탭에서 초록 체크 확인(보통 2~3분). 팀원은 새로고침만 하면 됩니다. 떠 있는 버전은 `server\VERSION.txt` 에 남습니다.
6. 기능·운영이 바뀌었으면 이 문서 사이트(`docs/`)와 [변경 이력](changelog.md)에 같이 반영합니다.

새 입력 항목을 추가할 때는 화면의 항목 정의(`FIELDS`)만으로 끝나지 않습니다. 엑셀 머리글 매핑·CSV 열·현황 양식·서버 마이그레이션까지 함께 손대야 합니다 — [엑셀 양식·업로드·내보내기](excel.md), [데이터 모델](data-model.md) 참조.

## 5. 절대 하지 말 것

!!! danger "이 6가지는 되돌리기 어렵습니다"
    1. **`hub.db` 를 덮어쓰지 않습니다.** 과제·일정·계정이 전부 들어 있는 파일 하나입니다. 옛 스냅샷을 다시 넣는 일도 하지 않습니다(설치 이후에는 서버판 데이터가 원본).
    2. **서버 PC에서 코드·배치를 즉석 수정하지 않습니다.** 수정은 저장소에서 하고 배포로 내려보냅니다. 서버에서 고친 내용은 다음 배포에 덮여 사라지고, 원인 추적도 불가능해집니다.
    3. **예약 작업을 SYSTEM 계정으로 만들지 않습니다.** 보안 제품 정책 때문에 등록 1분 안에 조용히 사라집니다. 반드시 로그인 계정 + S4U.
    4. **PowerShell 명령을 base64 로 감싸지 않습니다**(`-EncodedCommand`). 내용이 정상이어도 프로세스가 강제 종료됩니다.
    5. **설치용 배치를 이유 없이 재실행하지 않습니다.** 코드 갱신은 push → 자동 배포로 충분합니다. 재실행했다면 예약 작업 계정이 바뀌었을 수 있으니 등록 상태를 반드시 재확인합니다.
    6. **같은 PC의 다른 시스템(다른 포트·다른 러너·다른 폴더)은 건드리지 않습니다.** 파이썬 프로세스를 이름으로 일괄 종료하는 것도 금지 — 다른 팀 시스템이 함께 죽습니다.

## 6. 알려진 미결 · 향후 계획

| 항목 | 지금 상태 | 다음 담당자가 알아야 할 것 |
|---|---|---|
| 전산팀 Azure 이관 | 예정. 프론트·백엔드를 Azure 로, DB는 사내 포털 또는 Azure Database 로 옮기는 방향 | 이관 후 **접속 주소가 바뀌고**, 로그인이 **회사 MS 계정** 방식으로 전환될 예정입니다. 이 문서 사이트의 아키텍처·데이터 모델·인증·API 페이지가 이관 설계의 기초 자료입니다 |
| Artifact판 허브 | 폐기 방향 | 사내 서버판만 갱신합니다. Artifact판 데이터를 서버로 다시 넣지 않습니다 |
| https | 현재 사내망 http | 이관 시 적용 검토 |
| `Dockerfile` | 미작성 | Linux·컨테이너로 옮길 때는 Python 3.12 이미지에 `requirements.txt` 설치 후 uvicorn 실행, `hub.db`·`uploads` 를 볼륨으로 붙이는 구성이 전제입니다 |
| 담당자 계정 연결 | 팀원 가입이 끝나는 대로 관리자가 **1회 실행** | 미연결 과제는 담당자 본인이 수정할 수 없습니다. **데이터 점검** 워크플로우가 미연결 건수를 알려 줍니다 |
| 그룹 AX 대시보드 연동 | 엑셀 파일(그룹 양식) 전달 방식 | 직접 연동 계획은 없습니다 |

## 7. 사내 전용 정보의 위치

이 공개 문서에 없는 값은 아래에 있습니다. 인계 자리에서 **실물과 위치를 함께** 확인하세요.

| 필요한 것 | 어디에 |
|---|---|
| 허브 접속 주소(사내망), 서버 PC 식별 정보 | 사내 인수인계 문서 |
| 서버 PC 로그인 계정, 설치 실측 기록(설치 위치·파이썬 경로·예약 작업 설정값) | USB 패키지 안의 설치 기록 문서 |
| 최초 설치·USB 재생성·되돌리기 절차 | USB 패키지 안의 안내 문서와 서버 폴더의 `README` |
| GitHub 계정·러너 등록 토큰 | 문서에 적지 않습니다. 토큰은 필요할 때 저장소 화면에서 새로 발급(유효 1시간) |
| 관리자·팀원 계정 이메일 | 허브 화면(계정 관리)에서 확인. 문서·로그에는 가려서만 남습니다 |

## 8. 연락 체계

| 역할 | 담당 범위 |
|---|---|
| **자금팀 허브 관리자**(복수) | 가입·과제 승인, 계정·비밀번호, 데이터 내용 문의, 화면 기능 요청 |
| **자금팀 개발·운영 담당**(이 문서의 인계 대상) | 코드 수정·배포, 예약 작업·백업·진단, 장애 1차 대응 |
| **전산팀 담당** | 서버 PC 하드웨어·네트워크·보안 제품 정책, Azure 이관, 사내 계정 |

판단선: **허브 화면만 이상하다** → 운영 담당. **서버 PC 자체가 응답하지 않는다(핑 불가·전원 꺼짐)** → 전산팀.
팀원에게는 "회사 PC에서도 안 열리면 관리자에게 연락"으로 안내되어 있습니다.
