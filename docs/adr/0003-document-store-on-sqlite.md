# ADR-0003 · 문서형 저장소(SQLite 단일 표)

| 항목 | 내용 |
|---|---|
| 상태 | 채택 (2026-09-07) |
| 결정 | 컬렉션마다 표를 만들지 않고, `docs(coll, id, data JSON, version, updated_at)` 한 표에 모든 문서를 담는 문서형 저장소로 갑니다. |

## 배경

Artifact판 저장소는 '컬렉션(서랍) 안에 문서(JSON)를 넣는' 방식이었고, 화면 코드도 그 모양에 맞춰 쓰여 있었습니다. 서버판으로 옮길 때 두 갈래가 있었습니다.

| 길 | 문제 |
|---|---|
| 관계형 — 과제·일정·계정마다 표를 만들고 필드를 열로 | 화면 코드를 전부 고쳐야 하고, 입력 항목을 하나 늘릴 때마다 스키마 변경(ALTER)이 필요 |
| 문서형 유지 — 컬렉션/문서 모양을 그대로 흉내 냄 | 필드 단위 제약(NOT NULL 등)을 DB 가 걸어 주지 못함 |

허브는 항목이 계속 늘어나는 화면판입니다. 실제로 2026-09-08~09 사이에 그룹 등록 메모·과제번호·절감 7칸·첨부·사용안내가 차례로 추가됐습니다. 그래서 스키마 변경 비용이 결정을 갈랐습니다.

## 결정

문서형을 유지하고, SQLite 에는 표를 네 개만 둡니다.

| 표 | 열 | 용도 |
|---|---|---|
| `docs` | `coll, id, data(JSON), version, updated_at` | 모든 문서. `(coll, id)` 가 기본키 |
| `sessions` | `token, email, created_at, expires_at` | 로그인 세션 |
| `locks` | `key, holder, expires_at` | 편집 잠금(짧은 TTL) |
| `audit` | `ts, who, action, coll, id, detail` | 누가·언제·무엇을 저장·삭제했는지 |

컬렉션은 `projects`·`events`·`accounts`·`links`·`meta` 다섯 개이고, 문서 하나가 `data` 열의 JSON 한 덩어리입니다. 저장할 때마다 `version` 이 1 씩 올라갑니다. API 도 같은 모양입니다 — `GET/POST /api/db/{coll}`, `GET/PUT/PATCH/DELETE /api/db/{coll}/{id}`.

값 검증은 DB 대신 **화면(`hub.html`)과 서버(`server/app.py`) 양쪽 코드**가 담당합니다. 화면은 편의(버튼 숨김·필수 표시), 서버가 최종 판정입니다.

## 결과 (장점 · 감수한 단점)

**장점**

- 입력 항목 추가가 `FIELDS` 배열 한 줄(+ 필요하면 엑셀 머리글 매핑)뿐입니다. DB 는 손대지 않습니다.
- 화면 코드를 거의 그대로 옮겼습니다([ADR-0002](0002-single-frontend-with-adapter.md)).
- 데이터 전체가 파일 하나이고 문서 JSON 을 그대로 꺼낼 수 있어 이관이 쉽습니다.
- 필드 이름을 바꿀 때는 서버 기동 시 1회 마이그레이션 함수로 변환합니다(예: `migrate_savings()`).

**감수한 단점**

- DB 가 제약을 걸어 주지 않으므로 필수·형식 검사를 코드에서 빠뜨리면 그대로 저장됩니다. 그래서 규칙을 화면·서버 두 곳에 같은 논리로 두는 것을 개발 규칙으로 못 박았습니다.
- 조건 검색·집계를 SQL 로 하기 어렵습니다. 컬렉션을 통째로 읽어 브라우저에서 걸러내는 방식이라, 과제가 수천 건 규모로 늘면 방식을 바꿔야 합니다(현재 규모에서는 문제 없음).
- 필드 이름을 바꾸면 옛 문서와 새 문서가 섞이므로 마이그레이션 함수와 화면 별칭(ALIAS)을 함께 둬야 합니다.

## 되돌릴 때

관계형으로 가려면 `docs` 를 읽어 컬렉션별 표로 펼치는 변환 스크립트를 한 번 돌리면 됩니다(문서 JSON 의 키가 그대로 열이 됩니다). 화면의 저장소 호출부와 `shim.js` 를 함께 고쳐야 하므로, 백엔드를 새로 쓰는 이관 시점에 함께 판단하는 것이 맞습니다.
