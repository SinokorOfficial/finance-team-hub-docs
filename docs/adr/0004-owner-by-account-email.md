# ADR-0004 · 담당자 권한은 계정(이메일)으로만 판정

| 항목 | 내용 |
|---|---|
| 상태 | 채택 (2026-09-04) |
| 결정 | 과제의 수정·삭제·요청 권한은 담당자 '이름'이 아니라 과제 문서의 `ownerEmail`(로그인 계정)과 세션 계정이 일치할 때만 인정합니다. |

## 배경

과제 문서에는 처음부터 담당자 이름(`owner`)이 있었습니다. 초기 데이터가 팀 취합 엑셀에서 왔기 때문에 이름은 채워져 있었지만, 로그인 계정과 연결된 정보는 없었습니다.

권한을 이름으로 판정하면 문제가 두 개 생깁니다.

- **동명이인**: 이름이 같은 두 사람이 있으면 남의 과제를 고칠 수 있게 됩니다. 그룹 계열사까지 범위를 넓히면 실제로 발생할 수 있는 상황입니다.
- **표기 흔들림**: 엑셀에서 올라온 이름에 공백·직위가 붙거나 오타가 있으면 본인인데도 권한이 없게 됩니다.

이름은 '누가 담당인지 보여 주는 표시'로는 좋지만, 권한 판정의 근거로 쓸 수 없습니다.

## 결정

과제 문서에 `ownerEmail` 필드를 새로 두고, 담당자 판정은 이것만 봅니다.

```js
const isOwner = p => !!(me && p.ownerEmail
  && String(p.ownerEmail).toLowerCase() === String(me.email).toLowerCase());
```

서버(`server/app.py`)도 저장·삭제 때 세션 계정과 문서의 `ownerEmail` 을 같은 방식으로 다시 대조합니다. 화면이 버튼을 보여 주든 말든, 최종 판정은 서버입니다.

**기존 데이터 연결** — 관리자 화면에 `[담당자 계정 연결 실행]` 버튼을 둡니다. 승인된 계정 중 **이름이 정확히 하나만 일치하는 경우에만** 자동으로 `ownerEmail` 을 채우고, 둘 이상 일치하거나 하나도 없으면 건너뜁니다. 남은 것은 관리자가 과제 편집 창에서 계정을 직접 고릅니다. 엑셀 업로드도 같은 규칙입니다 — `담당자 이메일` 열이 있으면 그 값을 쓰고, 비어 있으면 이름이 1:1 로 일치할 때만 연결합니다.

연결되기 전까지는 담당자로 이름이 적혀 있어도 **열람만** 가능합니다. 상세 창에는 `(계정 미연결)` 로 표시됩니다.

## 결과 (장점 · 감수한 단점)

**장점**

- 동명이인이 남의 과제를 고칠 경로가 없습니다.
- 권한 판정 근거가 로그인 세션 하나로 좁혀져서, 화면과 서버가 같은 논리를 쓰기 쉽습니다.
- 이름 표기는 자유롭게 바뀌어도 권한에 영향이 없습니다.

**감수한 단점**

- 팀원이 가입을 마치기 전까지는 담당자가 자기 과제를 고칠 수 없습니다. 그래서 팀 전원 가입 후 관리자가 연결을 1회 실행하는 절차가 인수인계 항목으로 남습니다.
- 이름이 여러 계정과 겹치면 자동 연결이 안 되므로 수동 확인이 필요합니다(의도한 동작입니다 — 틀린 자동 연결보다 미연결이 안전).

## 되돌릴 때

이름 기준 판정으로 돌아가려면 `isOwner` 와 서버의 대조 로직을 이름 비교로 바꾸면 되지만, 동명이인 위험이 그대로 돌아옵니다. 권장하지 않습니다. `ownerEmail` 자체는 표시용 이름(`owner`)과 별개 필드라, 남겨 둔 채 판정만 바꿀 수 있습니다.
