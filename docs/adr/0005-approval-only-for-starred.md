# ADR-0005 · ★ 과제는 승인 절차, 그 외는 담당자 직접 수정

| 항목 | 내용 |
|---|---|
| 상태 | 채택 (2026-09-07, v3.10) |
| 결정 | 그룹 대시보드 전달 대상(★, `toPlanning`)인 과제만 등록·수정·삭제에 관리자 승인을 거치고, ★ 아닌 과제는 담당자가 승인 없이 바로 저장합니다. |

## 배경

v3.x 초기에는 모든 과제 변경이 승인 절차를 거쳤습니다. 초안(`draft`) → 승인 요청(`pending`) → 관리자 승인(`approved`) 순서이고, 승인 전에는 팀 화면이 바뀌지 않습니다. 이유는 명확했습니다 — ★ 과제는 그룹 대시보드에 등록될 자료이고, 한번 나가면 밖에서 고치기 어렵습니다.

문제는 승인 부담이었습니다. 관리자가 병목이 되고, 담당자는 오타 하나 고치려고 승인을 기다립니다. 수정의 상당 부분은 자기 과제의 진행 상황·비고 갱신이고, 애초에 그룹으로 나가지 않는 과제도 있습니다. 전부 승인으로 묶으면 데이터가 낡은 채로 방치됩니다.

## 결정

승인이 필요한 기준을 **'그룹으로 나가는 과제인지'** 로 정합니다.

| 구분 | 등록·수정·삭제 |
|---|---|
| ★ 전달 대상 (`toPlanning: true`) | 초안 저장 → 승인 요청 → 관리자 승인/반려. 승인 전까지 팀 화면 미반영 |
| ★ 아님 + 승인 상태 + 담당자 본인 | 저장하면 팀 전체 화면에 바로 반영. 삭제도 직접 가능 |
| 관리자 | 언제나 직접 저장·삭제 |
| 조회 전용 계정 | 쓰기 전부 불가 |

화면은 이 판정을 `freeEdit()` 한 함수로 모으고, 서버는 같은 판정을 `owner_free()`(승인된 과제 + ★ 아님 + 담당자 계정 일치)로 다시 합니다.

**요청 객체 `req`** — 승인 절차를 타는 변경은 과제 문서 안의 `req{type, state, data, requestedBy, requestedByEmail, rejectNote}` 에 담깁니다. 요청을 별도 표로 만들지 않고, 바뀔 내용(`data`)을 요청 안에 넣어 두고 승인 시점에 본문으로 옮깁니다. 반려하면 본문은 그대로고 `rejectNote` 만 남습니다.

담당자가 자기 과제에 **★ 를 켜는 순간** 그 저장부터 승인 절차로 넘어가며, 확인창으로 안내합니다. 서버 쪽 안전장치도 함께 둡니다 — 일반 계정은 `approval` 을 스스로 `approved` 로 만들 수 없고, 승인 절차 없이 문서를 통째로 덮어쓰는 것도 막습니다.

## 결과 (장점 · 감수한 단점)

**장점**

- 그룹으로 나가는 자료는 여전히 관리자가 전량 확인합니다(데이터 품질).
- 팀 내부용 과제는 담당자가 즉시 갱신합니다(승인 병목 제거).
- 승인이 필요한지가 화면의 ★ 하나로 눈에 보여서 규칙을 설명하기 쉽습니다.

**감수한 단점**

- 담당자 직접 저장은 되돌리기가 없습니다(이전 내용이 자동 복구되지 않음). 저장 전 확인창으로 알리고, 나중에 [수정 이력](0010-server-side-history.md)을 서버가 남기도록 보완했습니다.
- 규칙이 두 갈래라 화면·서버 양쪽에 같은 논리를 둬야 합니다. 한쪽만 고치면 어긋납니다.
- 직접 저장도 팀 화면에 바로 반영되므로 필수 항목 검사를 적용합니다(v3.21). 못 채운 항목이 있으면 '임시저장' 으로 두고, 목록에 '보완필요' 배지가 붙습니다.

## 되돌릴 때

전량 승인으로 되돌리려면 `freeEdit()` 과 `owner_free()` 를 항상 거짓으로 만들면 됩니다(데이터 변경 없음). 반대로 승인을 아예 폐지하려면 `req`·`approval` 을 읽는 코드를 걷어내야 하는데, 이미 저장된 문서에 두 필드가 남아 있으므로 마이그레이션이 필요합니다.
