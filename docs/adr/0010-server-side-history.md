# ADR-0010 · 수정 이력은 서버가 남긴다

| 항목 | 내용 |
|---|---|
| 상태 | 채택 (2026-09-09, v3.21) |
| 결정 | 화면이 보낸 이력 값을 믿지 않고, 서버가 저장 직전·직후 문서를 비교해 **바뀐 항목만** `history` 표에 기록합니다. |

## 배경

[ADR-0005](0005-approval-only-for-starred.md) 로 ★ 아닌 과제는 담당자가 승인 없이 바로 저장하게 됐습니다. 편하지만 **되돌리기가 없습니다** — 잘못 고쳐 저장하면 이전 내용이 사라지고, 누가 언제 무엇을 바꿨는지 확인할 방법이 없었습니다.

기존 `audit` 표는 '누가 언제 어느 문서를 저장·삭제했다'까지만 남깁니다. 문제를 확인하려면 **무엇이 무엇으로 바뀌었는지**가 필요합니다. 이력을 화면에서 만들어 보내는 방법도 있었지만, 그러면 브라우저가 보낸 값을 그대로 믿게 됩니다(이름을 다르게 적거나 이력을 빼고 보낼 수 있음).

## 결정

서버의 문서 저장 함수(`doc_put`)가 직접 비교해 기록합니다.

| 항목 | 내용 |
|---|---|
| 표 | `history(ts, coll, id, who, name, action, changes)` + `(coll, id, ts)` 인덱스 |
| 대상 | `projects` 컬렉션만 |
| 기록 내용 | 바뀐 항목의 `{k: 필드키, a: 이전값, b: 이후값}` 목록 |
| 값 길이 | 200자까지 잘라 저장 |
| 사람 이름 | **서버 세션의 계정 이름**(화면이 보낸 값이 아님) |
| 동작 구분 | 이전 문서가 없으면 `create`, 있으면 `update`, 삭제는 `delete` 한 줄 |

**매번 바뀌는 메타는 제외합니다** — `updatedAt`·`updatedBy`·`createdAt`·`createdBy`·`requestedAt`·`approvedAt`·`ord` 등. 이걸 빼기 때문에 **내용 변경이 없으면 한 줄도 남지 않습니다**(저장 버튼만 눌러도 이력이 쌓이지 않음).

승인 요청 객체(`req`)는 통째로 비교하지 않고 `종류 + 상태` 로 요약합니다. 첨부(`files`)처럼 배열인 값은 파일 이름을 이어 붙이거나 건수로 요약하고, 참/거짓은 '예/아니오' 로 씁니다.

**조회** — `GET /api/history/{coll}/{id}?limit=30` (로그인 필요, 최대 100건). 화면에서는 과제 상세 창의 접이식 「수정 이력」을 펼치면 최근 30건이 보입니다. 필드 키를 사람이 읽는 항목명으로 바꾸는 표는 화면이 가지고 있습니다 — 서버는 항목명 표기를 알 필요가 없으므로 키만 남깁니다.

**`audit` 표와의 차이** — `audit` 은 모든 컬렉션과 파일 업로드·삭제까지 '누가·언제·어떤 동작' 을 남기고 운영·점검 때 DB 로 직접 봅니다. `history` 는 `projects` 만 대상으로 '무엇이 무엇으로 바뀌었는지' 를 남기고 팀원 누구나 상세 창에서 봅니다. 목적이 달라 함께 둡니다.

## 결과 (장점 · 감수한 단점)

**장점**

- 담당자 직접 저장으로 내용이 사라져도, 무엇이 어떻게 바뀌었는지 화면에서 바로 확인합니다.
- 이름을 세션에서 가져오므로 기록을 위조할 수 없습니다.
- 메타 제외 덕분에 의미 없는 줄이 쌓이지 않아 이력이 짧고 읽기 쉽습니다.
- 화면이 이력을 만들지 않으므로 엑셀 업로드 같은 다른 저장 경로도 자동으로 남습니다.

**감수한 단점**

- 200자를 넘는 긴 항목은 잘려 저장되므로 **원문을 완전히 복구할 수는 없습니다**. 복구 수단이 아니라 추적 수단입니다.
- 저장마다 이전 문서를 한 번 더 읽고 비교합니다(현재 규모에서는 체감 없음).
- 자동 정리가 없어 계속 쌓이므로 DB 크기를 볼 때 함께 봐야 합니다.
- 필드 키를 그대로 남기므로, 필드 이름을 바꾸면 옛 이력의 항목명을 알 수 없게 됩니다.

## 되돌릴 때

기능을 끄려면 `doc_put` 의 이력 기록 호출과 상세 창의 접이식 영역을 빼면 됩니다. 이미 쌓인 `history` 표는 남겨 둬도 다른 동작에 영향이 없습니다. 완전한 복구까지 원하면 문서 전체 사본을 버전마다 남기는 방식이 필요한데, DB 크기와 맞바꾸는 결정이므로 별도 ADR 로 다뤄야 합니다.
